请求生命周期防护
- per-client request_mutex 在任何 SDK 任务创建之前初始化，保护列表插入、摘链、三处 dispatcher 遍历以及向匹配请求队列的非阻塞发送。
- SPI I/O、阻塞等待、JSON 解析、callback、reply_clear 均在锁外。
- request 超时/写入失败后先互斥摘链，再 drain 回复队列、delete 队列、free request。dispatcher 无法继续持有已摘链队列引用。
- 修复 request malloc 空指针、queue 创建失败时未初始化 ListItem、删除空队列；修复 client malloc 后先 memset 的 OOM 缺陷。

创建/销毁与真实双核内核依据
- 先 suspend 两个 worker，有界等待至双方 eTaskGetState == eSuspended；任一仍 Running/其他状态则不 delete/free。等待上限 100ms。
- 当前固定 IDF 使用 FreeRTOS-Kernel/tasks.c：taskIS_CURRENTLY_RUNNING（215）检查两个 core；eTaskGetState（1624-1676）先在 xKernelLock 下检查 Running；vTaskSuspend（1964-2100）请求远核 yield，并不保证返回时已停稳；vTaskDelete（1385-1461）只有非 Running 路径同步 prvDeleteTCB。故不能把直接 vTaskDelete 或 host 同步 mock 当作 SMP 停稳保证。
- 在 owner 阻止并发 task resume/API 的合同下，确认双方 eSuspended 后 delete 才可同步释放静态 TCB/stack。Delete 后不再对旧句柄调用 eTaskGetState。
- del 明确拒绝 inited=true 和 active request。调用者必须预先停止 callback、I/O、外部 API/resume；不能从 worker callback 销毁自身。App 无运行中 del，不改变正常运行流程。
- mutex 获取及 worker 等待各有 100ms 上限。失败返回 TIMEOUT，所有资源和句柄保留，安静后可重试；构造失败 worker 无法停止时，保留未发布的隔离 client、日志提示 cleanup deferred 并返回 TIMEOUT。这个罕见路径会泄露隔离资源，避免远核 UAF；不提供自动回收承诺。
- runtime 并发关闭需要独立关闭握手/引用计数，不在本候选范围。对任意持锁回调强制 suspend 并不安全。

确定的 buffer/reply 修复
- rx_buffer_size、tx_buffer_size 必须正数；分配 RX size+1，并检查 size < SIZE_MAX。read 容量 len 保持原值，满容量 data[pos]=0 有独立终止字节。
- dispatcher 的 INIT reset 在 reset queue 前逐项 receive+reply_clear；它是该队列唯一 producer，monitor 已接走的本地 reply 不碰。tasks 停稳后 del/构造失败亦 drain 再删除队列。
- reset/register_callback/ota_start 的 process suspend 前先获得 request mutex，挂起后即释放。只避免挂起 mutex 持有者；不宣称这些基线 reset 流程具备完整跨核 I/O 静止握手。
